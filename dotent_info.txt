## .NET build/publish/test & msbuild/vstest Integration**

Merging the Build/Publish, and Test stages into a single stage, aligning with the approach used in Maven builds. This consolidation aims to reduce artifact (e.g., `*.obj` files), minimize cache reloads for dependency libraries, and streamline initial setup time.

### **Output of this Combined Stage:**

- Publish Files
- Project Bin Directory
- NuGet Package (`.nupkg``) Files
- Veracode Zip File
- Test Coverage Result

The process involves executing the following commands in order:

**dotnet:**

```bash
dotnet build/publish ...
dotnet test ...
dotnet package ...
```

**msbuild/vstest:**

```bash
msbuild /t:Build;Test;Publish ...
```

## Recommended Changes (Risk Reduction for Future Enhancements)

The following changes are recommended to mitigate risks during future releases, as this Documentation's execution requires a completely new implementation. These adjustments provide an opportunity to address potential issues proactively through regression and application testing. Additionally, they allow the possibility of requesting applications to switch to this Documentation release specifically to resolve bugs blocking their pipeline processing.

- **.NET Tool Installation:** Install .NET tools into the `$CI_PROJECT_DIR` as a shared global directory when necessary.
- **Wix Library Handling:** Use the Wix extension tool to add Wix libraries instead of relying on custom code that checks NuGet locations.
- **Log Statements:** Replace `HostWrite` log statements with a standardized logging function for consistency and improved readability.
- **Backward Compatibility:** Introduce a `dotnet_framework_build` setting (Windows or Linux). If set to "legacy," the existing build logic will remain unchanged, ensuring compatibility with current pipelines.
- **Code Coverage:** Toolkit will *not* add coverage libraries to application projects. Applications are responsible for adding these references themselves before running the pipeline. This avoids dependency on Toolkit for coverage and reduces support overhead.  
Coverage checks have been moved from the Test stage to the combined Build/Test stage. For backward compatibility with `dotnet_build_framework="legacy"`, add the required coverage package (with the latest version) *before* the build command; this can prevent version conflict issues in some cases.
- **Wix Versioning:** The Wix version should be read directly from the Wix project file, rather than relying on a default value or input parameter within Toolkit.
- **NuGet Publish and Zip Publish:** NuGet publish will *only* upload `.nupkg` files to Nexus when `NUGET_PKG_API` is configured. Zip publish will only handle Nexus artifact setup.The existing implementation handles publish and nuget publish both together.
- **Observability Monitor:** Some .NET jobs do not include the `begin observability` step. This omission causes the `begin observability` entry to be added after the `after observability` entry, resulting in an improper pairing of observability monitor logs.

## Deprecation of Certain Inputs

Increasing the number of inputs does not result in a linear increase in project setup complexity. To reduce the effort required for project setup and Toolkit support, we will eliminate unnecessary inputs. Although these inputs are still used in builds when `dotnet_platform_build` is set to `legacy`, they will no longer be utilized by the pipeline for `windows` or `linux` environments.

The following inputs are being deprecated:

- **dotnet_publish_project_file:** Replaced with 'Solution Filter'.
- **dotnet_source_folder:** The solution (`*.csproj`) will now be read to determine the list of project directories.
- **dotnet_tests_folder and dotnet_test_filter:** Project lists will be extracted from the solution file, and tests will be identified based on these projects.
- **dotnet_test_proj_pattern:** Application setup coverage packages should now be configured directly within the project (`*.csproj`) instead of being added by the Toolkit pipeline using this pattern.
- **dotnet_microsoft_testing_platform_enable:** The project (`*.csproj`) will now be read to determine whether the Microsoft Testing Platform is in use.
- **dotnet_publish:** This input is no longer necessary since publish is now automated for TargetFramework builds. For `zip publish`, use the `nexus_artifact` input, and for NuGet publishing, provide the `nuget_publish_key`.
- **dotnet_pack_cmdline_options:** Customization of packing options should now be handled directly within the project (`*.csproj`) to maintain consistency across local testing and the Toolkit pipeline.
- **dotnet_build_runner and dotnet_win_runner_tag:** These inputs are no longer utilized to decide which window runner to employ.
- **dotnet_build_method:** The project  (`*.csproj`) configuration will determine whether to use 'dotnet' or 'msbuild' for building. Ensure all projects within the solution share consistent build settings.
- **dotnet_publish_mode:** The project (`*.csproj`) will now indicate whether it's a web publish.
- **dotnet_wix_enable:** Use the `wix_project_path` input to decide if WIX should be built.
- **dotnet_wix_output_name:** The output name will be read from the wix project settings.
- **dotnet_wix_bindpath:** It's advisable to reference WIX projects via the standard `bin` directory rather than using this bindpath setting, ensuring consistency in both local tests and the Toolkit pipeline.

This update aims to streamline the project setup process by reducing unnecessary inputs and enhancing consistency across different environments.
