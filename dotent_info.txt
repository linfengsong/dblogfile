# Implementation Refactoring - .NET Build Pipeline

This Documentation outlines a refactoring of the existing .NET build pipeline, leveraging a new implementation to address identified issues and improve overall convenience. This change presents an opportunity to enhance the current pipeline based on learnings from its operation.

## Core Principles for .NET Builds in Toolkit

The following principles guide the design of the new .NET build process and problem area in the existing Toolkit .NET pipeline:

* **Visual Studio Compatibility:** When building, testing, or publishing a .NET application in Visual Studio, it should function identically within Toolkit without requiring any additional configuration. Developers should not use Toolkit for troubleshooting project build/test/publish issues; those should be resolved locally in Visual Studio. Any Toolkit .NET pipeline error on build/test/publish should be reproducible in local Visual Studio.

* **Faithful Reproduction of VS Build:** Toolkit will replicate the Visual Studio build process exactly, whether building an entire solution or a solution filter. This includes generating identical error messages to those produced by Visual Studio. Toolkit will not introduce any custom build processing.

* **Solution-Driven Builds:** Toolkit builds and publishes solely based on the `.sln` (solution) file or `.slnf` (solution filter) file. Direct project build/publish is not supported. This aligns with how Visual Studio operates when building projects.

* **Pre-validated Application Code:** Toolkit assumes that applications have already passed basic syntax checks and unit tests in a local Visual Studio environment. It is not designed to identify these fundamental issues in the pipeline.

* **Support Platform Build:** Visual Studio allows setting up the build platform (e.g., `ANY`, `x64`). While this feature could be enhanced in future releases, implementing it would not introduce high risk. Once implemented, Toolkit will automatically clean up codes and test over 100% test coverage.

* **Standard Compliance**

Applications must comply with Microsoft and company coding standards for project setup. Toolkit will adhere to these standards but will not enforce them. No Toolkit-specific settings are required within solution or project files.

* **Single Publish Output**

Due to limitations in Nexus zip publish and Docker image uploads, the Toolkit .NET pipeline currently supports only a single publish output. For multiple outputs, applications must use solution filters to divide the build into separate solution filter files for each publish target.

* **.NET Publish and Nuget Publish**

The current version of the Toolkit .NET setup combines `dotnet publish` and `nuget publish`. To reduce unnecessary tasks and avoid requiring application setup with two different secret access rights, these processes should be made independent. Additionally, currently NuGet publish does not use the build stage output to create the `.nupkg` file; instead, it rebuilds the entire solution build, causing duplicate build processing and potential conflicts with build outputs.

* **WIX Project Setup**

The Toolkit pipeline currently requires applications to write WIX settings that reference the publish output directory (_app). This should be changed to reference the .NET build output directory (bin) instead. This change will allow the WIX project to run locally and produce the same results as those generated by the Toolkit pipeline.

* **Veracode Scan**
Veracode scans only published files and does not scan WIX output or NuGet package files.

* **Veracode Test**

Since GCP projects do not support Veracode scans, there are no test cases to verify Veracode scans. A test stage should be added to validate the required Veracode parameters and ensure that the Veracode zip file is generated correctly in the pipeline.

* **SonarQube Duplicate Build**

The SonarQube implementation in Toolkit should be re-implemented to replace the Manager SonarQube version, avoiding duplicate solution builds. This will allow the same SonarQube scans as configured in Visual Studio by developers, reducing support questions. This task is significant and can be executed as a standalone effort.
