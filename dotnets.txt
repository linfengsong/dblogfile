## 5. Understanding Access Control

### 5.1 How Repository Validation Works

The system validates access through a multi-step process:

```mermaid
graph TD
    A[Tool Request] --> B[Path Extraction]
    B --> C[Filesystem Jail Check]
    C --> D{Git Repository?}
    D -->|No| E[ACCESS DENIED<br/>Not in Git repo]
    D -->|Yes| F[Git Root Resolution]
    F --> G[Cache Check]
    G --> H{Cache Hit?}
    H -->|Yes| I[Return Cached Decision]
    H -->|No| J[Git Remote Extraction]
    J --> K[Pattern Matching]
    K --> L{Pattern Match?}
    L -->|Yes| M[ACCESS ALLOWED]
    L -->|No| N[ACCESS DENIED]
    M --> O[Update Cache]
    N --> O
```

### 5.2 Configuring Access Patterns

**Administrators** configure access via regex patterns in the workspace ConfigMap:

```yaml
# Example allow patterns
allowed_patterns:
  # All repositories in 'engineering' group
  - "^engineering/.*$"
  
  # Specific project and its forks
  - "^team/core-service(@.*)?$"
  
  # All frontend projects
  - "^.*/frontend-.*$"
```

**Pattern Examples**:
- `^engineering/.*$` - All repos in engineering group
- `^team/project-name$` - Specific project only
- `^.*-service$` - All repositories ending with "-service"
- `^team/.*@v2$` - Specific branch pattern

## 7. Troubleshooting and FAQs

### 7.1 Common Issues and Solutions

| Issue | Possible Cause | Solution |
|-------|---------------|----------|
| "ACCESS DENIED: Repository Governance" | Repository not in allow patterns | Check with admin about access configuration |
| "Tool not available" | Tool is in blacklist | Use alternative approach or request tool whitelist |
| "Budget exceeded" | Reached $10 weekly limit | Wait until Monday or request quota increase |
| "No Git repository found" | File not in tracked Git repo | Move file to authorized repository |
| "Path traversal attempt blocked" | Trying to access outside `/home/coder` | Stay within workspace directory bounds |

### 7.2 Frequently Asked Questions

<detailsstrong>❓ Why can't Claude write code for me?</strong></summary>

**Learning Accelerates Ownership**: When you author code based on architectural guidance, you build deeper understanding and ownership of the solution. This leads to better maintenance, debugging, and future development.

**Quality Improves with Review**: Your own critical evaluation, combined with peer review, catches issues that AI-first workflows often miss. Claude's role is to prepare you for effective review, not replace it.

**Compliance Requires Intention**: Certain codebases have regulatory or security requirements that mandate human authorship and review cyclesdetails>

<detailsstrong>❓ How are access decisions cached?</strong></summary>

Access decisions are cached **in-memory only** for security:

- **Scope**: Single Claude Code session only
- **Storage**: Process memory, not disk
- **Security**: User cannot tamper with cache decisions
- **Reset**: Cache cleared when Claude process ends
- **Performance**: ~10-50ms overhead reduced to ~1-5ms after cache hit

This prevents privilege escalation while maintaining performance for repeated repository access.

<summary><strong>❓ Can I request additional tools or access?</strong></summary>

Yes, through proper channels:

2. **Tool Access**: Some tools may be enabled for specific use cases with security review
3. **Budget Increase**: Teams with dedicated AI licenses can define custom budgets

All requests follow the governance framework to maintain security and compliance standardsdetails>

<detailsstrong>❓ What happens if I try to bypass restrictions?</strong></summary>

The system is designed with **multiple defense layers**:

1. **Managed Physics**: Tools disabled at runtime level
2. **Bypass Prevention**: `disableBypassPermissionsNode` prevents circumvention
3. **Filesystem Jail**: Paths outside `/home/coder` immediately rejected
4. **Credential Scrubbing**: Tokens redacted from all outputs

Attempts to bypass are logged and may trigger security reviews. The educational focus means we'd rather explain why restrictions exist than punish attempts.
</details>
